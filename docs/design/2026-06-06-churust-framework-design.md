# Churust — Design Spec (v1)

**Date:** 2026-06-06
**Status:** Approved (design), pending implementation plan
**Name origin:** Churro + Rust

## 1. Summary

Churust is a backend web framework written in Rust, inspired by Kotlin's Ktor.
Goal: **simple, secure, robust, easy to learn**. It provides a Ktor-like
developer experience — an application engine, a routing DSL, an
`install(plugin)` system, and a phased interceptor pipeline — built on top of a
battle-tested async stack (tokio + hyper + rustls). Churust owns the ergonomic
layer; it does not reimplement byte-level HTTP parsing or TLS.

## 2. Goals & non-goals

### Goals
- Ktor-faithful mental model: app engine, `routing { }`, `install(Plugin)`,
  phased pipeline, a single `call` context object per request.
- Hybrid handler API: `call`-style by default, opt-in typed extractors.
- Secure by default: body-size limits, request timeouts, panic isolation
  (a panicking handler returns 500, never crashes the server), no version
  banner leak, opt-in TLS via rustls.
- Easy to learn: a hello-world server in <15 lines; clear, small, well-bounded
  units.
- Fully testable in-process (no socket bind required) so every feature ships
  with unit + integration tests.

### Non-goals (v1 — deferred to v2, YAGNI)
- WebSockets
- Sessions / cookies plugin
- Response compression
- HTTP/3
- Built-in templating
- A full DI container (v1 ships a typed shared-state map only)

## 3. Foundation decisions (locked)

| Decision | Choice |
|----------|--------|
| Async runtime / HTTP / TLS | tokio + hyper (HTTP/1.1 + HTTP/2) + rustls |
| Handler API | Hybrid — `call` context default, opt-in typed extractors |
| v1 built-in plugins | ContentNegotiation (JSON), CallLogging, CORS, Authentication |
| Crate layout | Cargo workspace (umbrella + core + macros + per-plugin crates) |
| Config | Code DSL + `churust.toml` + env override |
| Pipeline model | Custom phased onion (approach A) — Ktor-faithful, owned by us |
| Edition / MSRV | edition 2021, MSRV stable 1.96 |

## 4. Workspace layout

```
churust/                  workspace root
  Cargo.toml              [workspace] members + shared deps
  churust/                umbrella crate: re-exports + `prelude`, feature flags
  churust-core/           engine, routing, pipeline, call, config, error, state, test harness
  churust-macros/         #[churust::main] proc-macro (tokio runtime + config load)
  churust-json/           feature "json"     → ContentNegotiation plugin (serde_json)
  churust-logging/        feature "logging"  → CallLogging plugin (tracing)
  churust-cors/           feature "cors"     → CORS plugin
  churust-auth/           feature "auth"     → Authentication plugin (Bearer/JWT, Basic)
  examples/
    hello/                minimal text server
    api/                  JSON CRUD API using all v1 plugins
```

Umbrella `churust` re-exports core + enables plugins via Cargo features
(`features = ["json", "logging", "cors", "auth"]`), so users depend on one
crate. `prelude` module brings the common imports into scope.

## 5. Core types (`churust-core`)

### 5.1 `Call`
The single per-request context object (Ktor's `ApplicationCall`).

- **Request side:** method, URI, path, query, headers, captured path params,
  body (lazily read; size-limited stream).
- **Response side:** a response builder — status, headers, body. Responses are
  set via `call.respond_*` helpers or returned values via `IntoResponse`.
- **Attributes:** a typed `TypeMap` for per-call data (e.g. auth principal set
  by the Auth plugin and read by a handler).
- **App state handle:** access to shared application state (see §10).

Helper surface (illustrative):
```rust
call.method(); call.path(); call.query("q"); call.header("authorization");
let id: u64 = call.param("id")?;          // path param, parsed
let body: NewUser = call.receive_json().await?;   // requires json plugin
call.respond_text("hi").await?;
call.respond_json(&user).await?;
call.respond_status(StatusCode::CREATED).await?;
```

### 5.2 Handlers — hybrid via extractors
- `Handler` trait with blanket impls for async closures/functions of arity
  `0..=N` (N≈12), generated by a declarative macro in core.
- `FromCall` extractor trait: `async fn from_call(call: &mut Call) -> Result<Self>`.
- `&mut Call` (and `Call`) implements the handler-argument path directly, so the
  **call-style handler is just the one-argument extractor case** — this is how
  "hybrid" is achieved without two parallel APIs.
- `IntoResponse` trait for return values and for `Error`.

```rust
// call-style
r.get("/", |call: &mut Call| async move { call.respond_text("hi").await });

// extractor-style (opt-in)
r.get("/users/{id}", |Path(id): Path<u64>| async move { Json(load(id).await?) });
```

Built-in extractors: `Path<T>`, `Query<T>`, `Header<T>`, `Json<T>` (json
feature), `State<T>`, and `&mut Call` itself.

### 5.3 Errors & responses
- Handlers return `Result<impl IntoResponse, churust::Error>`.
- `Error` carries a status + message + optional source; default `IntoResponse`
  maps it to an appropriate HTTP response.
- A StatusPages-lite hook lets apps override status→response rendering
  (`app.on_error(|err, call| ...)`).

## 6. Routing

- Radix/trie router keyed on (method, path-pattern).
- Patterns: static segments, `{name}` single-segment capture, `{name...}`
  trailing wildcard. Captures parsed on demand via `Path<T>` / `call.param`.
- Nested, scoped DSL with per-scope middleware (route-local plugins/interceptors):

```rust
routing(|r| {
    r.get("/", index);
    r.route("/api", |r| {
        r.intercept(require_auth);          // scope-local middleware
        r.get("/users/{id}", get_user);
        r.post("/users", create_user);
        r.route("/admin", |r| { /* nested */ });
    });
});
```

- Match resolution: most-specific-wins (static > param > wildcard); 405 vs 404
  distinction (path matched but method didn't → 405 with `Allow` header).

## 7. Pipeline (phased onion)

- `Middleware` trait:
  ```rust
  #[async_trait-ish]
  trait Middleware {
      async fn handle(&self, call: &mut Call, next: Next<'_>) -> Result<()>;
  }
  ```
  (Implemented with manually boxed futures or `async_trait`; decided in plan.)
- **Phases** (ordered insertion points), Ktor-style:
  `Setup → Monitoring → Plugins → Call → Fallback`.
  Plugins register interceptors into a named phase; order within a phase is
  install order.
- `Next` holds the remaining chain; calling `next.run(call).await` proceeds
  inward (onion model). A middleware may short-circuit by not calling `next`.
- The router itself runs at the `Call` phase; the matched handler is the
  innermost layer.

## 8. Plugin system

- `Plugin` trait: `fn install(self, app: &mut AppBuilder);` Plugins are
  builder-configured value objects (Ktor's `install(Plugin) { config }` becomes
  `install(Plugin::new().setting(x))`).
- Application builder:

```rust
Churust::server()
    .install(CallLogging::default())
    .install(Json::new().pretty(false))
    .install(Cors::permissive())
    .install(Auth::bearer(|token| async move { verify(token).await }))
    .routing(routes)
    .start()
    .await?;
```

### v1 built-in plugins
1. **ContentNegotiation (`churust-json`)** — serde_json receive/respond;
   `call.receive_json::<T>()`, `Json<T>` extractor, `respond_json`.
2. **CallLogging (`churust-logging`)** — per-request tracing span: method, path,
   status, latency; configurable level/format.
3. **CORS (`churust-cors`)** — configurable allow-origins/methods/headers,
   credentials, max-age; `permissive()` and strict builders; handles preflight.
4. **Authentication (`churust-auth`)** — pluggable schemes; v1 ships **Bearer/JWT**
   and **Basic**. Sets an authenticated principal into `Call` attributes;
   `require_auth` middleware + `Principal<T>` extractor; unauthenticated → 401
   with proper `WWW-Authenticate`.

## 9. Engine

- tokio `TcpListener`; per-connection hyper service.
- For each request: build `Call` → run pipeline (phases → router → handler) →
  write hyper response.
- rustls TLS opt-in (`.tls(cert, key)` or `[tls]` in config).
- Graceful shutdown on SIGINT/SIGTERM: stop accepting, drain in-flight,
  configurable grace period.
- HTTP/1.1 and HTTP/2. This document originally claimed HTTP/2 was enabled via
  hyper, which was not true at the time — `Cargo.toml` requested only hyper's
  `http1` feature and there was no ALPN or h2c code anywhere. Corrected
  2026-07-25, and then made true: the engine now uses hyper-util's `auto`
  builder, which negotiates h2 over TLS via ALPN and h2c by prior knowledge in
  plaintext.

## 10. App state / DI

- Typed shared-state map (`TypeMap`) on the application, cloned-Arc handle into
  each `Call`.
- Register: `.state(Db::connect().await)`.
- Consume: `State<Db>` extractor, or `call.state::<Db>()`.
- v1 is intentionally a typed registry, not a full DI graph.

## 11. Configuration

- Sources merged with precedence: **defaults < `churust.toml` < env
  (`CHURUST_*`) < code DSL**.
- File (serde + toml):
  ```toml
  [server]
  host = "0.0.0.0"
  port = 8080
  [server.limits]
  max_body_bytes = 1048576
  read_timeout_ms = 30000
  [tls]
  cert = "cert.pem"
  key  = "key.pem"
  ```
- Env override example: `CHURUST_SERVER_PORT=9090`.
- Code DSL always wins, so tests and embedding can force values.

## 12. Security defaults (secure by default)

- Max request body size (configurable; sane default e.g. 1 MiB).
- Read/write/idle timeouts (configurable defaults).
- **Panic isolation:** handler panics caught → 500 response; server keeps
  running. Logged via tracing.
- No framework/version banner in responses.
- Auth plugin returns correct 401/403 with standard headers; never leaks
  whether a user exists (constant-ish behavior left to app logic, framework
  doesn't leak).
- TLS via rustls (modern cipher defaults) when enabled.

## 13. Macros (`churust-macros`)

- `#[churust::main]` — wraps `async fn main`, sets up the tokio runtime and
  loads config (analogous to `#[tokio::main]`). Keeps examples clean.
- No `#[handler]` / routing attribute macros in v1 (extractor blanket impls make
  them unnecessary). Revisit in v2 if ergonomics demand.

## 14. Testing harness (`churust-core::test`)

- `TestClient` drives the assembled application **in-process**, invoking the
  request pipeline directly without binding a TCP socket.
- API mirrors a tiny HTTP client:
  ```rust
  let app = build_app();
  let client = TestClient::new(app);
  let res = client.get("/users/1").send().await;
  assert_eq!(res.status(), 200);
  assert_eq!(res.json::<User>().await.name, "Ana");
  ```
- Enables fast, deterministic unit + integration tests for routing, plugins,
  extractors, error mapping, and security limits. **Every shipped feature gets
  unit tests; cross-cutting behavior gets integration tests** (per project rule).

## 15. Example "hello world" (target ergonomics)

```rust
use churust::prelude::*;

#[churust::main]
async fn main() -> Result<()> {
    Churust::server()
        .install(CallLogging::default())
        .install(Json::new())
        .routing(|r| {
            r.get("/", |call: &mut Call| async move {
                call.respond_text("Hello from Churust 🌀").await
            });
            r.get("/users/{id}", |Path(id): Path<u64>| async move {
                Json(User { id, name: "Ana".into() })
            });
        })
        .start()
        .await
}
```

## 16. Build order (high level — detailed in the implementation plan)

1. Workspace skeleton + `churust-core` types (`Call`, `Error`, `IntoResponse`).
2. Router (radix, params, 404/405).
3. Pipeline (phases, `Middleware`, `Next`, onion).
4. Handler/extractor system (`FromCall`, blanket impls, built-in extractors).
5. Engine (hyper service, tokio listener, shutdown) + security defaults.
6. Config (toml + env + DSL precedence).
7. App state / DI.
8. Test harness (`TestClient`).
9. Plugins: json → logging → cors → auth (each with tests).
10. `#[churust::main]` macro.
11. Examples (hello, api) + docs/README.

Each step is TDD: tests first, then implementation, then verify.

## 17. Open questions resolved as defaults (override anytime)

- WebSockets/sessions/compression → v2.
- async-trait vs hand-boxed futures for `Middleware` → decided during plan
  (lean toward minimal/no-macro if ergonomics allow).
- JWT library choice (e.g. `jsonwebtoken`) → decided during plan.
